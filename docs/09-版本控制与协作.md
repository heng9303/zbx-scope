## 四、拿到地址后执行（本轮不做，等你发地址）

```bash
# 0) 先按 GitHub 账号修正首次提交作者（尚未 push，amend 完全安全）
git config user.name "<GitHub 用户名>"
git config user.email "<GitHub 邮箱，或 <owner>@users.noreply.github.com>"
git commit --amend --reset-author --no-edit

git remote add origin <你发来的地址>
git remote -v                      # 核对，确认没加到别的仓库
git branch -M main
git push -u origin main

# 打首个版本 tag（与 dist/releases/v4.2-full 对应）
git tag -a v4.2.0 -m "v4.2.0 · P0 安全稳健 + 产品路线总纲"
git push origin v4.2.0
```

推送前会再跑一次第六节的敏感信息扫描。
若 GitHub 仓库误勾了初始化文件，用 `git pull --rebase --allow-unrelated-histories origin main`
合并后再推，**不要**用 `--force`。

## 五、安全红线（这一节最重要）

### 5.1 绝不入库

| 内容 | 为什么 |
|---|---|
| `real/config.json` | 含各实例 API Token、只读账号口令、Basic Auth 口令 |
| `audit.jsonl*` | 真实调用日志，可能含主机名与查询参数 |
| `real/data/*.json` | 早期调试抓取的真实 API 响应 |
| `.workbuddy/` | 本地会话与个人记忆数据（**只忽略，不删除**） |
| 文档中的明文口令 | `docs/00`、`docs/06` 曾写过测试环境口令，**入库前已统一替换为 `<PASSWORD>`**；`deploy/release.sh` 不再硬编码口令，改读本地词表 `deploy/redact-words.local.txt`（已忽略、不入库） |

提交前固定跑一次：

```bash
# 1) 确认敏感文件确实被忽略（应逐条输出命中）
git check-ignore -v real/config.json real/audit.jsonl dist/ handoff/ .workbuddy/

# 2) 扫已暂存内容里的真实凭据特征（长 token / Bearer / 非占位的 password 值）
git grep --cached -nIE 'Bearer [A-Za-z0-9]{20,}|"(token|password)"[[:space:]]*:[[:space:]]*"[A-Za-z0-9]{16,}"' \
  || echo "未发现明文凭据"

# 3) 人工复核文档里的口令写法（应只看到占位符）
git grep --cached -niE 'password|口令' -- docs/ deploy/README-部署.md | head -30

# 4) 确认待提交清单
git status --short
```

> ⚠ **`--cached` 必须写在匹配模式之前**。写反时 git 会报
> `option '--cached' must come before non-option arguments`，而 `|| echo` 会把这个错误
> 吞成"未发现明文凭据"，造成**假通过** —— 本项目初始化时实际踩过一次，务必留意退出码。
> 更稳的写法是先看 `echo $?`：`1` 才是"确实没匹配到"。

### 5.2 内网信息

`docs/` 与 `deploy/` 的部署示例里写有内网地址（`10.51.x.x`）和实例规模。
**如果仓库设为 Public，这些内容会公开**，推送前需要先统一替换为占位符
（`<ZABBIX_API_URL>` / `<DEPLOY_HOST>`）并复核文档仍可读。
选择 Private 则无需改动 —— 这也是推荐 Private 的主要原因。

### 5.3 许可证与商标

- 名称用 `zbx` 前缀而非 `zabbix-`，避免被误认为官方项目；README 已写明非官方；
- 仓库尚未选择 License，Private 可暂不设置；Public 前需确定许可证口径，
  并保留 ECharts（Apache-2.0）等第三方声明；
- Zabbix 服务端为 AGPLv3，本项目仅通过 API 读取数据、不链接其代码，
  正式开源前请自行确认合规口径（本文不构成法律意见）。

## 六、协作规范

### 提交信息

```
<type>: <一句话说明>          # 例：feat: 图形对比视图收藏
```
`feat` 新功能 / `fix` 修复 / `docs` 文档 / `test` 测试 / `chore` 构建与配置 / `refactor` 重构。
一次一整批：一批对应一次（或一组）提交，提交说明里带上 [07](07-页面迭代路线图.md) 的批次编号，
例如 `feat(P1-1): 图形对比视图收藏`。

### 分支

- `main` 始终可运行；
- 单人小步迭代可直接提交到 `main`，**每完成一整批必须打 tag**；
- 改动面大或需要审核的批次（如 B0-2 功能开关、P3 模块化）开 `feat/<批次>` 分支，
  本地自检通过后再合并。

### Tag 与 Release

| 约定 | 说明 |
|---|---|
| 版本号 | 语义化：功能批次升 minor（`v4.3.0`），修 bug 升 patch（`v4.2.1`） |
| 首个 tag | `v4.2.0`，对应 `dist/releases/zbx-console-v4.2-full` |
| Release 附件 | 用 `bash deploy/release.sh --tag <tag> --note "<说明>"` 生成的 `.tar.gz` |
| 变更说明 | 从 [06-变更日志](06-变更日志.md) 对应小节摘取 |

### 每批收尾（在 [07](07-页面迭代路线图.md) 第三节 SOP 后面追加两步）

```
8. git add -A && git commit -m "<type>(<批次>): <说明>"
9. git tag -a <版本> -m "<说明>"     # 整批交付才打 tag
```

**Git tag 是源码的权威版本锚点**；`dist/releases/<tag>` 是「含文档、已脱敏、带哈希清单」的
对外交付包，两者互补，不要互相替代。
