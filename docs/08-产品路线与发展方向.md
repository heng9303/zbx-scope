## 一、结论先行

**Q1｜后续还能不能生成"原基础功能"的版本来交付？**

**能，但不建议靠"翻出旧代码"来做。** 三条路径里只有一条值得走：

| 路径 | 做法 | 判断 |
|---|---|---|
| A 快照复原 | 从 `index.v3.html.bak` / `dist/*.tar.gz` / `handoff/` 拼回旧版 | ⚠ 只适合一次性考古。**项目没有 git 仓库**，历史快照不完整、无标签无哈希、且都落后于 v4.2；拼出来的版本没有经过当前回归，交付风险高于收益 |
| B 目录分叉 | 复制一份 `baseline/` 单独维护 | ❌ 不推荐。从此每个 bug 要修两遍，必然分叉 |
| C **功能档位（推荐）** | 同一份代码，用 `edition` 配置决定开放哪些能力，打包时按档位产出 | ✅ 同源、零分叉、随时可产出，回归只跑一份代码 |

在 C（本文称 **B0**）完成前，**可以用"冻结快照"方式立即交付当前稳定版**（脚本已备好，见第七节）；
B0 完成后，`Baseline / Standard / Full` 三档随时可生成，不需要再翻旧文件。

**Q2｜产品往哪走？**

从「Zabbix 二次开发试验品」收敛为 **「多版本 Zabbix 统一只读运维视图」**：
主场景是**值班看板**与**拓扑/资产关系速览**，不写 Zabbix、不替代官方 UI、不引入框架。
理由见第五节 —— 三个真实版本（4.0 / 7.0 / 8.0）同时跑通，是这套系统最难复制的资产，
比"再做一个 Grafana"更值得押注。

**下一批建议**：**B0 版本分层与发布治理**（改动小、直接解锁 Q1），之后再做 P1 使用效率。
若你更想先看到页面变好用，也可以 P1 优先、B0 后置，两者无依赖。

### 2.4 三个结构性短板（本轮梳理新发现）

1. **盘点时没有版本控制**（2026-11-07 21:40 之前）：`git status` 返回 `not a git repository`。
   所有"旧版本"靠文件名和记忆定位，没有 tag、没有哈希、没有变更集，
   也没有"哪一版对应哪次验收"的对应关系。
   → **已解决**：用户决定对接 GitHub，本轮完成 `git init`、忽略规则、根 README 与
   [09-版本控制与协作](09-版本控制与协作.md)，并推送到 `heng9303/zbx-scope`（Public / SSH）。
   推送前完成内网地址脱敏。此后 **Git tag 是权威版本锚点**，
   `dist/releases/<tag>` 降级为对外交付包。
2. **交付包与代码不同步**：`handoff/` 和 `dist/*.tar.gz` 都停在 v4.1。
   现在把它们交给外部 AI 审核，得到的会是**过时结论**（会建议补 P0 已做的事）。
   任何对外交付前必须重新打包。
3. **能力堆在一个平面**：`app.js` 3345 行，基础功能与增强功能没有边界标识，
   所以"只交付基础功能"目前只能靠删代码，不能靠配置。B0 要解决的就是这个。

## 三、产品定位（重新表述）

### 3.1 一句话

> 把多个不同版本的 Zabbix 当成**只读数据源**，做一层更贴合运维阅读习惯的统一视图，
> 让值班时"当前有什么问题 / 哪台机器不对 / 链路大概怎么连"在几秒内看清。

### 3.2 谁在用、什么场景

| 角色 | 场景 | 现在怎么解决 | 我们提供什么 |
|---|---|---|---|
| 值班工程师 | 交接班、盯当前告警 | 官方 Problems 字段多、噪音大 | 按严重度/组聚合、下钻、14 天趋势、大屏模式（待做） |
| 网络/系统运维 | 排查"页面没数据"、看端口收发 | 开多个页面、分不清"没数据"和"采集失败" | 健康模型 + 原因聚合 + 多序列同图对比 |
| 运维负责人 | 给领导/同事讲整体状况 | 截图拼凑 | KPI 摘要、拓扑速览、CSV 导出（待做） |

### 3.3 边界：和 Grafana / 官方 UI 的分工

- **不替代官方 UI**：配置、告警确认、维护窗口仍在 Zabbix 做；
- **不做采集与存储**：数据源全部来自 Zabbix API，不留本地时序库；
- **不做写操作**：这是服务端硬闸门，不是"前端不显示按钮"；
- **差异化在"跨版本 + 值班视角"**，不在图表种类 —— 图表种类比不过 Grafana，也不必比。

### 3.4 三条不可动摇的产品原则

1. **只读是架构约束**，不是使用约定；
2. **零依赖、拷目录就能跑**，不为工程优雅引入构建链；
3. **版本差异只进 `CAPS`**，业务代码里不写 `if (version === "4.0")`。

## 四、能力分层：把"原基础功能"定义清楚

「原基础功能」此前没有明确口径。本文按 **v3 能力集** 定义，并把它固定为 `Baseline` 档：

| 层 | 能力 | 引入版本 | Baseline | Standard | Full |
|---|---|---|:---:|:---:|:---:|
| L0 数据链路 | 只读代理 / 白名单 / 审计 / 多实例切换 | v2–v3 | ✅ | ✅ | ✅ |
| L1 基础视图 | 问题总览（筛选、抽屉、趋势） | v2–v3 | ✅ | ✅ | ✅ |
| L1 基础视图 | 主机列表、主机详情（问题/监控项/触发器/接口/图形/资产） | v3 | ✅ | ✅ | ✅ |
| L1 基础视图 | 图形：单项 + 原生 graph + 区间选择 | v3 | ✅ | ✅ | ✅ |
| L1 基础视图 | 拓扑首版：sysmap + 自动聚类 | v3 | ✅ | ✅ | ✅ |
| L2 诊断与对比 | 监控项健康模型、无数据回退、"只看异常" | v4 | ➖ | ✅ | ✅ |
| L2 诊断与对比 | 多序列对比 / 收发配对 / 双轴 / 深链 | v4 | ➖ | ✅ | ✅ |
| L2 诊断与对比 | 拓扑三模式 + 规划编辑 + 置信度 | v4 | ➖ | ✅ | ✅ |
| L2 诊断与对比 | 接口与只读保证页、五档响应式 | v4 / v4.1 | ➖ | ✅ | ✅ |
| L3 工程与交付 | Basic Auth / 审计轮转 / 统一错误态 / Docker 部署 | v4.2 | ➖ | ✅ | ✅ |
| L4 后续增强 | 收藏、搜索、CSV、大屏、跨实例聚合… | P1–P2 | ➖ | ➖ | ✅ |

> **Baseline = v3 能力集**（只读 + 问题/主机/详情/单项图形/拓扑首版），
> 不含 v4 之后的诊断、对比、规划编辑与部署化能力。
> 若你的口径是"更小的基础版"（例如只要问题 + 主机两页），见第九节待决策项 D-1。

### 三档怎么产出（B0 的目标形态）

```
一份代码 real/
   ├─ /api/meta 下发 edition: baseline | standard | full + features{}
   ├─ 前端按 features 决定导航项 / 按钮 / 模式入口是否渲染与是否可执行
   └─ 打包脚本按 edition 产出对应交付包（同一份源码，不同清单与配置）
```

关键点：**档位是"能力开关"，不是"删文件"**。
`baseline` 档仍需保留服务端只读闸门与安全加固（安全能力不随档位降级），
因此 `access` / `audit_rotate` 属于全档位必开，不进开关表。

## 五、发展方向：四条候选与取舍

| 代号 | 方向 | 吸引力 | 主要代价 / 风险 | 判断 |
|---|---|---|---|---|
| D1 | **值班大屏工具**：收敛成一块顶屏，字号大、自动轮播 | 场景最清晰、最容易被认可 | 天花板低，做完就没增量；仍是"一个页面" | 作为**交付形态**保留（P2-1 大屏模式），不单独当主线 |
| D2 | **多版本统一运维门户**：4.0/7.0/8.0 一套视图、跨实例聚合 | 现有资产最独特，别人最难复制；已跑通三版本 | 每个新能力都要过 CAPS 兼容性，回归成本 ×3 | ✅ **推荐主线** |
| D3 | **拓扑与资产关系平台**：自动推断 + 手工规划做成资产图 | 差异化最高、领导最直观 | 连线数据源弱，依赖人工修正，容易变成"看起来准其实不准" | 作为 D2 下的**能力域**投入，不单独押注；坚持标注置信度 |
| D4 | **只读数据服务 / 开放 API**：给别的系统供数 | 想象空间大 | 权限模型、合规、鉴权全要重做，与"内网小工具"定位不匹配 | ❌ 明确不做 |

**推荐**：以 **D2 为主线**，D1 作为其中一种交付形态，D3 作为差异化能力域，D4 不做。

**为什么不是 D1**：当前 6 个视图已经具备完整值班能力，再往"大屏"收敛会放弃多实例/拓扑这些已投入的能力；
**为什么不是 D3 单独做**：拓扑连线的推断证据不足（同网段 60% 置信度），把它当主产品会持续被"这线准不准"质疑；
**为什么是 D2**：`4.0.50 / 7.0.32 / 8.0.0` 三套完全不同的 API 契约同时跑通、且差异收敛在 `buildCaps()`，
是已验证的、可复用的工程资产，继续放大它的边际成本最低。

## 七、版本交付机制（Q1 的落地）

### 7.1 现在已经能做的：冻结快照

```bash
bash deploy/release.sh --tag v4.2-full --edition full --note "P0 后的首个稳定基线"
```

产出 `dist/releases/zbx-console-v4.2-full/` 与同名 `.tar.gz`，内含：

- `code/`：`server.py` + `public/`（含 ECharts vendor）+ 脱敏配置模板；
- `deploy/`：Dockerfile、compose、部署脚本、配置模板；
- `docs/`：`README` + 00–08（**自动脱敏真实口令**）；
- `README-交付.md`：版本、档位、启动方式、验证基线、已知限制；
- `manifest.json`：版本号、时间、档位、说明、**每个文件的 SHA-256 与大小**。

脚本会先做语法自检（`node --check` / Python AST）、再脱敏、再算哈希；
**默认不带真实凭据**，需要带凭据须显式 `--with-config`（仅限本机 → 目标服务器）。

### 7.2 B0 之后能做的：按档位产出

```bash
bash deploy/release.sh --tag v5.0-baseline --edition baseline
bash deploy/release.sh --tag v5.0-standard --edition standard
bash deploy/release.sh --tag v5.0-full      --edition full
```

三份包来自同一份源码，区别只在 `config` 的 `edition` 与打包清单；
`baseline` 档的冒烟用「基础功能子集断言」，不要求 L2+ 能力存在。

> 当前脚本对 `--edition baseline/standard` 会**明确报错并提示先完成 B0-2**，
> 不会悄悄打出一个"看起来是基础版、其实功能全在"的包 —— 这是刻意设计。

### 7.3 每次交付固定动作

```
① 本地自检（07 第三节）
② release.sh 冻结 → 得到 tag + manifest 哈希
③ 交付包只从 dist/releases/<tag> 出，不从 real/ 直接拷
④ 更新 07 状态表 + 06 变更日志，记录 tag 与哈希前 8 位
⑤ 远程部署仍走 deploy.sh / package.sh，两者互不替代
```

**回滚**：`dist/releases/` 里的任一历史 tag 都是完整可运行快照；
远程侧另有镜像 tag 与宿主机 `config.json`（不随重建丢失），两层回滚互不冲突。

## 八、度量与红线

### 8.1 用这几个数判断"有没有变好"

| 指标 | 当前基线 | 目标 |
|---|---|---|
| 冒烟断言数 | 20（每实例） | 随功能单调上升，不下降 |
| 响应式检查 | 7 档 × 4 页 × 4 断言 = 112 | 新增页面必须纳入 |
| 首屏可用时间（4.0，157 主机） | 人工复核截图无中间态 | 保持，不因功能增加而劣化 |
| 只读闸门 | `host.update` 被拦截 | 任何批次后都必须复验 |
| 交付可复现性 | 无 | 每个 tag 有 manifest 哈希 |

### 8.2 红线（不变）

- 不做告警确认、维护窗口等**任何写操作**；
- 不引入前端框架/打包器，保持"拷目录就能跑"；
- 不替换 Zabbix 主 UI，不建本地时序库；
- 不删除远程服务器上其他开发环境的容器 / 网络 / 卷，`docker compose down -v` 禁止；
- 不做用户体系与权限（靠 Zabbix 账号权限 + 网络层访问控制）；
- 拓扑持续标注置信度，不承诺等同于物理拓扑。
