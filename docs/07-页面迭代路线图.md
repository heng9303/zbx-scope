## 三、每轮迭代 SOP（固定流程，别跳步）

```
1. 确认范围     ← 从本文挑一批/一项，明确"这次不改什么"
2. 本地改动     ← 只改 real/ 下的文件
3. 本地自检
     node --check real/public/js/app.js
     node --check real/tests/*.mjs
     python3 -c "import ast;ast.parse(open('real/server.py').read())"
     node real/tests/ui-smoke.mjs zbx7 http://DEPLOY_HOST:8770
     node real/tests/ui-smoke.mjs zbx4 http://DEPLOY_HOST:8770
     node real/tests/responsive.mjs zbx7 10683      # BASE 环境变量指向远程
     node real/tests/shots.mjs zbx4 10084           # 人工看一眼截图
4. 部署到远程
     cd real && tar -czf - <改动文件> | ssh netops-dev 'cd /opt/zbx-console && tar -xzf -'
     # 只改前端 → 无需重建镜像（静态文件在镜像里，需重建！）
     ssh netops-dev 'cd /opt/zbx-console && docker compose up -d --build'
     ⚠ 注意：public/ 和 server.py 已 COPY 进镜像，改了必须 --build
5. 远程复验     ← 重复第 3 步，确认容器里跑的是新代码
6. 收尾
     更新本文状态表 + docs/06-变更日志.md + .workbuddy/memory/YYYY-MM-DD.md
7. 出包（凡是对外交付 / 给其他 AI 审核，必做）
     bash deploy/release.sh --tag <版本> --note "<本批说明>"
     ⚠ 不要直接把 handoff/ 或旧的 dist/*.tar.gz 发出去，它们是 v4.1 快照
8. 提交（提交前先看 docs/09 第五节安全红线）
     git add -A && git commit -m "<type>(<批次>): <说明>"
9. 整批交付才打 tag
     git tag -a <版本> -m "<说明>"
```

**回滚点**：镜像保留上一版 tag 即可秒回；`config.json` 在宿主机上不随重建丢失；
审计在 named volume 里，`down` 不加 `-v` 就不会丢；
`dist/releases/<tag>` 是完整可运行的源码级快照，可作为第三层回滚。

**绝对禁止**：`docker compose down -v`、`docker system prune`、
删除 `/opt` 下其他目录、改动其他项目的容器/网络/卷。

## 五、给下一轮接手者的提示

- 改前端前先读 `03-前端扩展指南.md` 第九节（响应式五档断点）与第十节（自检命令）；
- 接新 Zabbix 版本先读 `02-API契约与版本适配.md` 的 10 条实测坑；
- 所有版本差异只改 `buildCaps()`，不要在业务代码里写 `if (version === "7.0")`；
- 异步回写一律带竞态守卫 `if (S.xx.id !== id) return;`，否则快速切实例会串数据；
- 表格一律 `table-layout:fixed`，隐藏列用语义 class，别用 `:nth-child`。
