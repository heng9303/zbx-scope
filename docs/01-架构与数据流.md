# 01 · 架构与数据流

> 目标：让新接手的人 10 分钟内知道「数据从哪来、经过谁、存在哪、页面怎么拿到」。

---

## 一、三层结构

```
┌──────────────────────────────┐
│  浏览器 SPA（public/）        │  零构建、零依赖（除本地 vendor 的 ECharts）
│  index.html + css + js        │  状态集中在闭包变量 S
└──────────────┬───────────────┘
               │  POST /api_jsonrpc.php   {jsonrpc, method, params}
               │  GET  /api/meta | /api/log | /api/ping
┌──────────────▼───────────────┐
│  只读代理（server.py）        │  单文件、仅标准库、绑定 127.0.0.1
│  白名单闸门 + 认证 + 审计      │  凭据只在此进程内，不下发浏览器
└──────────────┬───────────────┘
               │  http(s)://<zbx>/api_jsonrpc.php
┌──────────────▼───────────────┐
│  Zabbix（8.0 / 7.0 / 4.0…）  │  只被读，从不被写
└──────────────────────────────┘
```

**为什么必须有代理**：浏览器直连 Zabbix 需要把 Token/密码放进前端，任何人按 F12 就能拿到，
且无法阻止页面被改造成写接口。代理把凭据留在服务端，并把「只读」做成代码级闸门。

---

## 二、目录职责

| 路径 | 职责 | 运行时是否必需 |
|---|---|---|
| `server.py` | 只读代理 + 静态文件服务 | 是 |
| `config.json` | 实例列表（upstream / 认证方式 / 凭据） | 是 |
| `public/index.html` | 页面骨架（~477 行，只含结构，不含样式与脚本） | 是 |
| `public/css/app.css` | 全部样式，按区块注释分区 | 是 |
| `public/js/app.js` | 全部前端逻辑，单 IIFE | 是 |
| `public/vendor/` | ECharts 5.5.1 本地副本 | 是 |
| `tests/ui-smoke.mjs` | 零依赖 CDP 冒烟（断言） | 否（开发用） |
| `tests/shots.mjs` | 零依赖 CDP 整页截图（人工复核） | 否（开发用） |
| `audit.jsonl` | 每次真正转发的调用记录，追加写 | 运行时生成 |
| `data/*.json` | **早期手工抓取的样本快照**，用于分析契约，页面不读 | 否 |

> `data/` 容易误解：它不是缓存，也不是数据源。删掉不影响运行。

## 三、代理（server.py）

### 3.1 路由

| 路径 | 方法 | 用途 |
|---|---|---|
| `/api/meta` | GET | 实例列表、白名单、转发/拦截计数、最近被拦记录 |
| `/api/log` | GET | 内存环形日志最近 200 条（供「接口页」展示） |
| `/api/ping` | GET | 存活探测 |
| `/api_jsonrpc.php` | POST | 唯一的数据通道，方法受白名单限制 |
| 其它 | GET | 静态文件（根路径映射到 `index.html`，禁止 `..`） |

### 3.2 只读闸门

```python
READ_ONLY = { "apiinfo.version", "host.get", ... }   # 共 34 个
if method not in READ_ONLY:
    # 记账 → 返回 JSON-RPC error → 请求根本不会发往 Zabbix
```

这一层是「不修改源 Zabbix」的**硬保证**：即使前端被改、有人手工构造请求，
`host.update` / `item.update` / `event.acknowledge` 之类也只会得到
`Blocked by read-only proxy`。

### 3.3 认证

| 模式 | 适用版本 | 实现 |
|---|---|---|
| `token` | 5.0+ | 请求头 `Authorization: Bearer <token>` |
| `login` | 4.0–6.x | `user.login` 换 `sessionid`，请求体带 `auth`；缓存 600s，会话失效自动重登一次 |

`login` 模式的两个细节（都是实战踩出来的）：

- **参数名随版本变化**：`<=5.2` 用 `{user, password}`，`5.4+` 用 `{username, password}`。
  代码先取 `apiinfo.version`（结果缓存），再决定字段名，**失败只尝试一次**。
  早期版本会「失败后用另一个字段名再试一次」，结果 4.0 返回
  `unexpected parameter "username"`，把真正的密码错误覆盖掉，还白白多消耗一次失败计数。
- **失败原文必须透传**：`RuntimeError` 带上版本号、参数名、上游原文和排查提示，
  前端才能显示「密码不对」而不是白屏。

### 3.4 审计

每次真正发往 Zabbix 的调用追加一行 `audit.jsonl`：

```json
{"ts":1746000000,"profile":"zbx8","method":"history.get","ms":140,"count":968,"ctype":"rows","params_keys":["from","itemids","to","value_type"]}
```

被拦截的写操作也会记一行（`blocked: true`）。内存里保留最近 400 条供 `/api/log`。

## 四、前端（app.js）

### 4.1 模块顺序

文件顶部的注释就是目录，改代码时请沿用这个顺序，不要横插：

```
基础设施 → 格式化 → 顶栏 → 启动取数 → 组装行 → 渲染总览
→ 主机页 → 主机详情 → 图形页 → 绘制 → 拓扑页 → 接口页 → 抽屉 → 路由 → 事件绑定
```

### 4.2 状态字典 `S`

所有可变状态集中在 `S`，没有组件级状态、没有全局散变量：

| 键 | 内容 |
|---|---|
| `meta` / `version` / `profiles` | 代理元信息、Zabbix 版本、实例列表 |
| `hosts` / `hostById` / `groups` | 主机全量、按 id 索引、组计数 |
| `problems` / `rows` / `triggers` | 原始问题、**解析后的展示行**、triggerid→trigger |
| `alerts` / `media` / `events14` / `bars` | 告警发送成败、媒介、14 天事件、柱状图数据 |
| `graph` | 主机、图形/监控项列表、区间、已选序列、pairMap、ECharts 实例 |
| `topo` | 模式、模型、规划数据、连线/删除态、缩放、拖拽中间态 |
| `filt` / `hostFilt` | 问题页 / 主机页筛选与排序 |
| `hd` | 当前主机详情：数据、分页、筛选、`lastData`、`probed` |

**约定**：`S.rows` 是「展示口径」，由 `S.problems + S.triggers` 经 `buildRows()` 解析而来；
新页面要展示问题，读 `S.rows`，不要自己再解析一遍 `problem.get`。

### 4.3 启动链

```
boot()
 ├─ GET /api/meta                  → 实例列表、白名单、计数
 ├─ apiinfo.version                → buildCaps(v) 写入 CAPS
 ├─ loadCore()  ← 8 个请求并发
 │    host.get ×1、problem.get ×1、alert.get ×4（计数×3 + 样本×1）、mediatype.get、event.get
 ├─ trigger.get（用 problem.objectid 批量反查）→ buildRows() / buildBars()
 ├─ renderAll()                    → 各页 DOM
 └─ applyRoute()                   → 按 location.hash 决定显示哪一页
```

`problem.get` 返回的对象里**没有主机字段**，`objectid` 就是 `triggerid`。
所以必须二次 `trigger.get(triggerids, selectHosts)` 才能拿到主机名——这一步在 4.x/7.x/8.x 通用，
不要试图用 `problem.get(hostids)` 省掉它（4.x 支持不稳定）。

### 4.4 版本能力矩阵 `CAPS`

页面**不判断版本号**，只读 `CAPS`。新增适配时改 `buildCaps()`，不在业务代码里写 `if (major>=7)`。

| 字段 | <7 | >=7 | 影响 |
|---|---|---|---|
| `groupField` | `groups` | `hostgroups` | 主机组字段名 |
| `groupSelect` | `selectGroups` | `selectHostGroups` | 查询参数名 |
| `mapNode` | `elementid` | `elements` | sysmap 节点主机 id 取值路径 |
| `problemHostids` | ≥6 才 true | true | 是否可用 `problem.get(hostids)` |
| `inventory` / `tags` | ≥4 | true | 资产、标签可选字段 |

### 4.5 路由表

| hash | 页面 |
|---|---|
| `#problems`（默认） | 问题总览 |
| `#hosts` | 主机列表 |
| `#host/<hostid>` | 主机详情 |
| `#item/<itemid>` | 单监控项图形 |
| `#items/<id1>,<id2>,…` | **多监控项对比**（顺序即颜色顺序，>8 截断） |
| `#graphs` / `#graphs/<graphid>` | 原生图形 |
| `#topo` | 拓扑（auto / map / plan 三模式在页内切换） |
| `#api` | 接口与只读保证（契约差异、白名单、调用日志） |

深链参数：`?profile=zbx7` 切实例，`?range=7d` 指定区间，
`?from=2026-10-13T00:00&to=...` 自定义区间，`?event=<eventid>` 直接打开问题抽屉。

## 五、一次「看某个端口收发」的完整数据流

```
用户点 #items/140403,140529
  → item.get(itemids=[...])                      拿名称/单位/value_type/健康字段
  → history.get(itemids=[...], history=0, from,to) 一次多取，按 itemid 归组
      └ 结果为空 → fetchRecent()：不限时间窗，sortfield=clock DESC, limit=160
                    └ 仍为空 → trend.get 小时聚合
  → drawSeries()  多单位自动开右轴、分单位统计、tooltip 按序列带单位
  → 若发生回退：横幅明示「该区间没有数据，最近一次采集是 X」
```

关键点：`history.get` 的 `history` 参数必须等于监控项自己的 `value_type`
（float=0、uint=3、str=4、text=2），**传错不会报错，只会静默返回空数组**——这是本项目最容易踩的坑。
