# 04 · 拓扑引擎

> 拓扑是本项目里唯一「数据不足以完全支撑、必须靠推断 + 人工修正」的模块。
> 本文说明它是怎么连的、置信度怎么来的、以及为什么不做成"自动画出真实物理拓扑"。

---

## 一、为什么不能"自动生成真实拓扑"

真实物理拓扑需要 LLDP/CDP 邻居表（每端口对端设备+端口），而 Zabbix 里通常只有：

| 数据 | 有 | 没有 |
|---|---|---|
| 主机清单、接口 IP、主机组 | ✅ | |
| sysmap 映射图（人工画的） | 部分环境有 | |
| LLDP/CDP 邻居（要有模板采集） | 少数环境有 | |
| 端口↔端口 的物理连接关系 | | ❌ 基本拿不到 |

所以本模块的定位是：**给出一张"够用的、可修正的"拓扑草图**，
把「哪里连哪里」的最终决定权交给人，而不是假装它等于物理事实。

---

## 二、三种模式

| 模式 | 数据来源 | 用途 |
|---|---|---|
| **自动拓扑**（默认） | 主机清单 + 主机组 + sysmap + LLDP + 网段推断 | 快速看懂"网络大概长什么样"、定位在警设备 |
| **Zabbix 映射图** | `map.get`（selements + links） | 环境里已有人工维护的映射图时，原样看 |
| **规划编辑** | 自动拓扑的结果 + 人工拖拽/连线 | 把草图修成"我方认可的拓扑"，可导出归档 |

三种模式共用同一套 `paintTopo()` 渲染，差别只在模型从哪来。

---

## 三、连线推断与置信度

四条来源按**置信度从高到低**合并，同一对节点只保留最高的那条：

```js
TOPO_KIND = {
  map:    { conf: 100, color:"#7FB3C8", dash:false },  // sysmap 里人工画的
  manual: { conf: 100, color:"#00A9C7", dash:false },  // 规划模式手工连的
  lldp:   { conf:  90, color:"#5FB3A1", dash:false },  // LLDP/CDP 邻居
  subnet: { conf:  60, color:"#B7C6D4", dash:true  }   // 同 /24 网段推断
}
```

`addLink()` 的合并规则：已存在同一对节点时，新来源置信度更高才覆盖。

### 3.1 sysmap（100%）

`map.get` 的 `selements[].elementid` 在部分版本为 `null`，主机 id 在 `elements[0].hostid`
（见 `CAPS.mapNode`）。取不到主机的元素（文字、图片）直接跳过。

### 3.2 LLDP/CDP（90%）

```
item.get(search.key_ = "lldp") + item.get(search.key_ = "cdp")
  → 取 lastvalue 文本
  → 在「主机名 / 可见名 / 接口 IP」三者构成的字典里做包含匹配
  → 命中且不是自己 → 建一条 lldp 边
```

这是**启发式**，不是协议解析。它假设邻居值里含有对端的主机名或 IP 文本，
常见的 `LLDP neighbour … SysName: SW-1_-2F-70.8` 这类值可以命中。
如果环境里的 LLDP 是对端 MAC/端口描述，匹配会失败——这是已知局限，不是 bug。

### 3.3 同网段（60%）

```
按 /24 前缀分组 → 每组里选一个 hub（hubScore 最高）→ 其余节点连到 hub
```

`hubScore` = `是网络设备 +100` + `类型=2 的接口数 ×10` + `接口总数` + `已停用 −50`。
即"端口最多的交换机当汇聚点"，符合大多数接入层组网。

**这条是纯推断**，所以画成虚线、置信度 60%，并在图例里标"推断"。

## 四、布局：货架式聚类

不是力导向图（力导向在 60+ 节点时会互相挤压、每次刷新位置乱跳）。用的是**可预测的货架排布**：

```
1. 按主机名前缀 / 首个主机组聚类
     SW-x…  → "SW-x"        （同名交换机归为一簇）
     CORE/FW/RT/AP-x → 取前缀
     其它   → 首个主机组名，没有则「未分组」
2. 簇排序：含 CORE 的排最前，其余按名称
3. 逐簇从左到右摆：
     列数 cols = clamp(2, 4, ceil(sqrt(n)))
     簇宽 = cols×152 + (cols-1)×14，簇高 = 24(标题) + rows×42 + (rows-1)×14
     当前行放不下（超过 1500px）就换到下一货架，货架高度取该行最高簇
4. 画布宽 = min(1500, 最右边界+18)，高 = 最后一个货架底部
```

常量在 `TOPO_NODE_W/H`、`TOPO_GAP_X/Y`、`MAXW`。改密度只动这几个数。

**节点位置优先级**：`规划数据里的坐标` > `自动布局坐标`。
所以手工拖过的节点刷新后不会跳回去。

## 五、绘制细节

### 5.1 连线形状

正交折线，不用曲线（曲线在密集区域会互相缠绕）：

```
两个节点中心 y 接近（<8px） → 水平直连 H
两个节点中心 x 接近（<8px） → 垂直直连 V
否则                        → V-H-V 三段折线（先竖、横、再竖）
```

### 5.2 节点配色

判定顺序（`topoNodeStyle`）：

| 条件 | 边框 | 说明 |
|---|---|---|
| `status=1`（已停用） | 灰 | 不参与告警着色 |
| `rank=2`（采集中断 / 不可达） | 红 `#E05252` | 设备整机不可达 |
| `severity>0` | 对应严重度色 | ≥4 用更深的底色 |
| `rank=1`（有异常但未达告警） | 黄 `#E8A33D` | |
| 其它 | 默认浅灰 | |

右上角小圆点是状态点，颜色与严重度一致。

### 5.3 链路告警

一条连线的颜色取**两端节点中最高的严重度**，并在 `title` 里注明
`端点告警：严重`。同时线宽从 1.4 加到 2.2。
这是"推断"，所以只在 tooltip 里说，不在图上加额外标记。

### 5.4 缩放

```js
S.topo.zoom      // 0.3 – 2.2，默认按宽度铺满
svg width/height = 像素值（model.W × zoom）
preserveAspectRatio = "xMinYMin meet"
```

**为什么不用 `width:100%`**：用百分比时，画布比容器高会被压扁，字小到看不清（实测 29%）。
现在按宽度算初始缩放（不低于 55%），容器 `overflow:auto`，宁可滚动也不缩字。

## 六、规划数据

### 6.1 存储

```js
localStorage["zbx.topo.plan.v1.<profile>"] = {
  nodes: { "<hostid>": {x, y} },        // 拖拽后的坐标
  links: [ {a, b} ],                    // 手工连线
  hidden: ["<idA>|<idB>", ...]          // 被删除的推断连线（按排序后的 key）
}
```

按 profile 隔离，切实例不会串。**只存浏览器本地，不写 Zabbix**。

`hidden` 是必要设计：删掉一条子网推断连线后，如果不记录"这对节点不要再画"，
下次重算推断它又会回来。用排序后的 `a|b` 作为 key，与方向无关。

### 6.2 导出 / 导入

导出为 JSON（含 `nodes/links/hidden` + 导出时间 + profile），可进版本管理或交给同事；
导入校验字段类型后整体替换。**导入不合并**，避免出现半旧半新的坐标。

### 6.3 清空

`清空` 按钮带 `confirm`，只清本实例的规划数据。

## 七、交互

| 操作 | 行为 |
|---|---|
| 单击节点（auto/map 模式） | 跳转 `#host/<hostid>` |
| 单击节点（plan 模式且未开连线） | 选中（高亮），不跳转 |
| 双击节点 | 始终跳转主机详情 |
| 拖拽节点（仅 plan 模式） | `pointerdown/move/up` 更新 plan.nodes 并重绘 |
| 连线模式 | 点第一个节点 → 提示"已选起点" → 点第二个 → 建边；同节点点击取消 |
| 删除模式 | 点一条连线 → 该边进 `hidden`（推断边）或从 `links` 移除（手工边） |
| 单击连线（auto 模式） | 显示 tooltip：来源、置信度、端点告警 |

拖拽用 Pointer Events 而不是 mouse 事件，是为了兼容触控板/触屏；
移动过程中只改坐标重绘，`pointerup` 时才落盘 `savePlan()`。

## 八、页面上的四张卡片

| 卡片 | 内容 | 用途 |
|---|---|---|
| 拓扑数据 | 节点/连线/在警节点/主机组/画布尺寸/规划条目数 | 一眼判断数据完整性 |
| 连线来源与置信度 | 各来源条数 + 颜色图例 | **让人知道哪些线是猜的** |
| 主机组在警分布 | 按组的在警主机条形 | 定位故障面 |
| 操作说明 | 当前模式下的可用操作 | 降低上手成本 |

「连线来源与置信度」这张卡是这个模块的诚实性所在——它明确告诉使用者
"54 条线里有 54 条是 60% 置信度的推断"，避免被当成资产拓扑。

## 九、已知限制

1. **LLDP 匹配是文本包含**，对端值不含主机名/IP 时会漏。
2. **同网段按 /24 假设**，跨网段（/22、/16）或三层组网会画错。
3. **一台主机只画一个节点**，多网卡多 IP 只取第一个（见 `hostIps`）。
4. **上限 80 节点**，超出截断（`buildAutoModel` 的 `slice(0,80)`），避免浏览器卡顿。
5. **不做环路检测**，推断边可能造出不存在的三角。
6. **规划数据不共享**，同一浏览器不同 profile 之间隔离，换机器要导出/导入。

这些都是为了让"草图可用"而做的取舍。需要更准，正确的路径是：
在 Zabbix 侧补 LLDP 模板采集，或人工维护 sysmap，让 100% 置信度的线占比上升。

## 十、扩展一个新的连线来源

以「按 OSPF 邻居表连线」为例：

```js
function ospfLinks(hosts) {
  var items = /* 已经取到的邻居项 */;
  var out = [];
  items.forEach(function (it) {
    var src = S.hostById[it.hostid];
    var dst = /* 解析 lastvalue 得到对端 hostid */;
    if (src && dst && dst !== src.hostid) addLink(out, src.hostid, dst, "ospf", it.name);
  });
  return out;
}
```

三步接入：

1. `TOPO_KIND` 加一项：`ospf: { label:"OSPF 邻居", color:"#8E7CC3", dash:false, conf:95 }`
2. `buildAutoModel()` 里按置信度顺序插一行：
   `ospfLinks(hosts).forEach(...)`（放在 `lldpLinks` 之后、`subnetLinks` 之前）
3. 「连线来源与置信度」卡片会自动统计（它遍历 `TOPO_KIND` 与模型里的 `links`）

不需要改 `paintTopo` / `bindTopoEvents` / 规划持久化——它们都按 `kind` 泛化处理。
